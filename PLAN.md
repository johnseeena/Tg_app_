# План: Telegram-приложение для управления AmneziaWG VPN

Дата: 2026-07-18
Масштаб: личный/друзья (до ~50 пользователей)
Интерфейс: Telegram Mini App
Сервер: разворачивается с нуля (Docker)

## Ключевое требование: конфиги не хранятся на сервере

Сервер обязан знать **публичный** ключ каждого peer (для маршрутизации трафика WireGuard/AmneziaWG) — это неустранимо. Но **приватный** ключ и готовый `.conf`-файл на сервере храниться не должны.

Выбран **вариант B (zero-knowledge)**:

1. Пара ключей WireGuard (curve25519) генерируется **на устройстве пользователя** внутри Mini App (JS/WASM), приватный ключ никогда не покидает телефон.
2. На бэкенд отправляется только **публичный ключ**.
3. Бэкенд добавляет peer в живой конфиг AmneziaWG (`wg set`, без рестарта туннеля), возвращает параметры сервера (endpoint, server pubkey, obfuscation-params, DNS, AllowedIPs).
4. Mini App собирает финальный `.conf` на устройстве, показывает QR/скачивание.
5. Конфиг не отправляется сообщением в чат (не оседает в облаке Telegram).

Отклонённый вариант A (сервер генерирует ключи и сразу удаляет приватный) — не выбран, т.к. приватный ключ кратковременно проходит через сервер и облако Telegram.

## Архитектура

```
Telegram
 ├─ Mini App (React+TS, Telegram WebApp SDK) — генерация ключей, QR
 └─ Bot (aiogram) — вход, уведомления
        │ HTTPS, initData HMAC-проверка
   Caddy (TLS, reverse-proxy)
        │
   Backend API (FastAPI)
     • auth по Telegram initData (HMAC-SHA256 токеном бота) + роли
     • rate-limit, аудит-лог
     • VPN-менеджер: add_peer/remove_peer/list через wg set
        │
   PostgreSQL: users, peers(pubkey, ip, лимиты) — БЕЗ приватных ключей/конфигов
        │
   AmneziaWG (VPN-контейнер)

Всё поднимается через docker-compose на одном сервере.
```

### Схема БД (минимум)
- `users` — telegram_id, role (`user`/`admin`), created_at, status
- `peers` — user_id, public_key, assigned_ip, name, traffic_limit, expires_at, created_at, revoked_at
- `audit_log` — actor_id, action, target, timestamp

### Разделение ролей
Роль определяется по telegram_id из проверенного initData против списка админов в env (не из тела запроса).

| Пользователь | Админ |
|---|---|
| Добавить устройство (QR/конфиг) | Список пользователей, поиск |
| Мои устройства, статус/трафик | Выдать/заблокировать/отозвать доступ |
| Отозвать своё устройство | Лимиты трафика и срока |
| | Вкл/выкл/рестарт VPN, ротация ключей сервера |
| | Просмотр нагрузки, аудит-лог |

      `/security-review`, рассчитанный на diff, не применим); найдено и
      исправлено:
  1. **Race condition в выдаче IP** — `ip_allocator.allocate_ip` читает
     «следующий свободный IP» без блокировки; при параллельных запросах два
     разных пользователя могли получить один IP. Фикс: partial unique index
     `uq_peers_assigned_ip_active` (уникален только среди неотозванных —
     бланковый constraint сломал бы переиспользование IP после revoke) +
     обработка `IntegrityError` как retryable 409.
  2. **Более глубокая версия той же гонки, найденная при реальном
     конкурентном тесте** (5 параллельных запросов через
     `ThreadPoolExecutor` из контейнера): даже с фиксом #1 порядок операций
     был «сначала `awg set`, потом insert» — несколько параллельных `awg
     set ... allowed-ips X/32` для РАЗНЫХ пиров перетирают друг друга на
     уровне WireGuard (AllowedIPs может принадлежать только одному пиру),
     так что «победившая» в БД запись могла остаться без реального маршрута
     на интерфейсе. Живой тест это подтвердил: пир в БД с `assigned_ip`,
     но `allowed ips: (none)` на интерфейсе. Фикс: переставил порядок —
     сначала insert (здесь Postgres реально сериализует через partial
     index), `awg set` только после успешного insert. Перепроверено тем же
     конкурентным тестом — оба сценария (гонка полностью в БД и гонка,
     доходящая до интерфейса) дают либо чистый 409, либо корректный
     уникальный маршрут, без «сирот».
  3. **`docker-compose.override.yml` мог утечь на прод** — пробрасывает
     порт backend в обход Caddy/TLS, Compose подхватывает его автоматически.
     Фикс: явное исключение в примере `rsync` в docs/DEPLOY.md + громкое
     предупреждение в самом файле.
  4. Мелкое: `.env` теперь `chmod 600` в инструкции (содержит
     `POSTGRES_PASSWORD`, `TELEGRAM_BOT_TOKEN`).
  - Принятые компромиссы (не фиксил, задокументировал): backend работает
    под root в контейнере (нужно для `NET_ADMIN`, стандартная практика для
    таких контейнеров); initData валиден 24ч (значение из документации

## Предостережения
- Обфускация AmneziaWG держится на приватности параметров (Jc/Jmin/Jmax/S1/S2/H1–H4) — не светить их в публичных репозиториях/логах.
- Ответственность за трафик VPN-сервиса и соблюдение законов юрисдикции/хостера — на владельце сервиса.

## Стадия 5: пивот AmneziaWG → VLESS+Reality (2026-07-19)

**Причина.** Реальное устройство пользователя не смогло подключиться через
мобильного оператора: `tcpdump` на сервере подтвердил, что пакеты от
телефона доходят и пересылаются в контейнер (не проблема DNS/портов), но
handshake никогда не завершается — похоже на DPI-блокировку протокола
WireGuard/AmneziaWG на уровне оператора. Решающее доказательство: **отдельная,
предустановленная официальная Amnezia (AmneziaWG)** на том же сервере
отказала идентично на той же сети — то есть дело не в конфигурации этого
проекта. Пользователь подтвердил, что это мобильный интернет оператора, и
явно выбрал переход на VLESS+Reality (через Xray-core) вместо тонкой
настройки обфускации AmneziaWG.

**Что изменилось.**
- Протокол: AmneziaWG → VLESS, транспорт: UDP/WireGuard → TCP + REALITY
  (сервер «занимает» настоящий TLS-handshake реального сайта — DPI видит
  обычный HTTPS к, например, www.microsoft.com).
- Контейнер `vpn` (amneziawg-go/tools) заменён на `xray` (`ghcr.io/xtls/
  xray-core`), см. `xray/Dockerfile`, `xray/entrypoint.sh`,
  `xray/config.json.template`.
- Управление пирами теперь через `xray api adu/rmu/statsquery` (gRPC
  HandlerService через CLI-обёртку), см. `backend/app/xray_manager.py` —
  заменяет `backend/app/vpn_manager.py` (`awg set/show`).
- Схема `peers`: удалена `assigned_ip` (у VLESS+Reality нет концепции
  выделения IP — это TCP-прокси, не сетевой интерфейс), `public_key`
  переименован в `client_uuid` — см. миграцию `0005_vless_reality.py`.
- Порт: вынесен на отдельный `XRAY_PORT` (по умолчанию 8443), не 443 —
  443 уже занят Caddy для самого Mini App/HTTPS; SNI-шаринг с Caddy
  рассматривался, но отклонён как излишне сложный/неверифицированный на
  фоне того, что блокировка похожа на DPI-уровня, а не на блокировку по
  порту — решение помечено как пересматриваемое, если окажется не так.
- Фронтенд: `frontend/src/wireguard.ts` (генерация X25519-пары на
  устройстве), `config.ts` (сборка `.conf`, хранение приватного ключа в
  localStorage) и `amnezia.ts` (qCompress-кодирование `vpn://`) удалены
  целиком, заменены на `frontend/src/vless.ts` — простая сборка
  `vless://{uuid}@{host}:{port}?...` без сжатия.

**Важный компромисс по «zero-knowledge» (честно, а не тихо).** Изначальное
жёсткое требование проекта — приватный ключ/конфиг никогда не должен
оказаться на сервере — было устроено вокруг асимметричной модели
WireGuard: сервер знает только *публичный* ключ, приватный никогда не
покидает устройство. У VLESS такой асимметрии нет: `client_uuid` — это
единственный bearer-credential, который `xray` сверяет на каждом
подключении, то есть по своей природе сервер обязан его знать и хранить
(иначе просто не сможет аутентифицировать клиента). Это архитектурное
свойство протокола, а не недосмотр реализации — так же устроены все
VLESS-панели (3x-ui, x-ui и т.п.). Смягчение: `client_uuid` — это не более
чувствительные данные, чем раньше был `public_key` (тоже хранился в БД в
открытом виде), просто теперь он *и есть* секрет, а не публичная половина
пары. Как следствие, `PeerOut`/`AdminPeerOut` теперь отдают `client_uuid`
всегда (не только один раз при создании) — это на самом деле улучшение UX
(ссылку можно восстановить, зайдя в приложение заново, а не только
«отозвать и добавить заново»), но стоит понимать, что это сознательный
отход от исходной модели угроз, принятый ради решения реальной проблемы
подключения.

**Не проверено на момент записи.** Реальное подключение через
заблокированную сеть оператора пользователя — конечный критерий успеха
всего пивота — ещё не протестировано. См. Стадию 5 в задачах.
